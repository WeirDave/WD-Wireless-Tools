Three fixes rooted in tonight's testing session, in order of impact:

1. **Uploads now keep the name you gave them.** Fixes the "I uploaded three files and Ekahau made three duplicates of my source file" surprise — root cause was Ekahau naming cloud projects from the `.esx`'s internal `project.name` metadata instead of the filename you sent. Now after every upload, if the two don't match, we auto-rename the cloud project to match the filename. What you upload is what shows up in cloud.
2. **Move-to-Site auto-match uses parent folder as the strongest signal for local files.** Before: 3 files in the same folder produced inconsistent auto-matches because filename fuzzy scores landed above/below the 0.5 threshold unpredictably. Now: a local file's parent folder is the primary signal, name fuzziness only a fallback.
3. **Bigger source-card scroll area** for large batches — bumped from a fixed 360px to `min(60vh, 520px)` so 20-30 items show without stingy scrolling.

Suite `v1.9.3 → v1.9.4`. WD Cloud Manager `v4.0.3 → v4.0.4`.

## What changed

### 1 · Upload auto-rename (the big one)

Backend `CloudManager.upload_project()` now compares Ekahau's returned project name against the local filename (minus `.esx`). If they differ, it calls `rename_project(new_id, desired_name)` immediately after the poll-until-visible loop confirms the upload.

**Why this matters:** Ekahau derives cloud project names from the internal `project.json`'s `project.name` field, NOT the filename. This is invisible to users. If you copy `Foo.esx` and upload it three times as `Test-A/B/C.esx`, Ekahau names all three cloud projects the same thing (whatever `Foo.esx`'s internal name is), which produces three cloud-side duplicates you can't tell apart.

Now:
- You upload `sample-project.esx` → Ekahau creates a project with whatever internal name → we immediately `PUT` a rename to `WD-Test-A` → cloud shows `WD-Test-A`.
- The rename is non-fatal: if it fails (rare), the upload still counts as successful — Ekahau just keeps the auto-name. Return payload includes `renamedTo` when the rename succeeded, so callers can surface it.
- Uses the existing `EkahauAPI.rename_project(pid, name)` API — no new endpoints, just wiring.

**Side effect for the deck's post-upload state:** now that cloud names match local filenames, the pair-matcher will find them and the freshly-uploaded files will show as SYNCED immediately after the auto-refresh, exactly as the mental model expects.

### 2 · Parent folder as primary auto-match signal

`_suggestSiteFor(itemName, sites, t)` now takes an optional target object `t`. For local-file targets, pass 1 checks whether the target's parent folder name matches any known site. If yes, that site is returned with score 2.0 — above any fuzzy/code match.

Prevents the case the maintainer hit tonight: 3 files sitting in the same `WD-Test-Site` folder got inconsistent auto-matches because "WD-Test-A" scored 0.5 vs "WD-Test-Site" (matched) but "WD-Test-B - Baseline" scored 0.4 (below threshold, no match). Now all 3 auto-match to WD-Test-Site regardless of what other tokens are in their filenames — because their parent folder IS WD-Test-Site.

Falls through to the existing pass-2 (site-code) and pass-3 (fuzzy) heuristics when the parent folder isn't a known site, so nothing that used to work stops working.

Legacy callers passing `(name, sites)` without the target object still work — they just don't get pass 1.

### 3 · Bigger source-card

CSS: `.mv-source-card { max-height: min(60vh, 520px); }`. On a laptop with a 900px viewport that's 540px capped at 520 → ~7 rows visible. On an ultra-wide 1440px viewport, still 520px (~7 rows). Below 900px, 60vh — proportional to available space.

The "Into" and "Will land at" sections below the source card stay visible because the modal itself is `.modal.file-op` with `max-height: 92vh` — plenty of headroom.
