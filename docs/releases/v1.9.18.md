WD Cloud Manager — matching gets a real backbone. WD now decides whether two files are the same project by reading the hidden UUID inside each `.esx`, not by guessing from name similarity and file size. Along the way we retired the size-based match guard that was silently rejecting legitimate pairs, added a plain-English confidence badge to every paired row, and gave users a manual "Link" escape hatch for the cases automation will never get perfect.

Suite `v1.9.17 → v1.9.18`. WD Cloud Manager `v4.4.1 → v4.5.0`.

## The bug that started this

the maintainer had two `.esx` files — one on Ekahau Cloud (9.2 MB), one on his local disk (1.5 MB) — that were obviously the same project. WD refused to pair them. Digging in with him:

1. **`_size_conflict` was rejecting the pair.** It fired when both sides were >500 KB and the ratio exceeded 5×. Ratio: 9.2/1.5 = 6.13×.
2. **But the sizes weren't comparable in the first place.** the maintainer downloaded the cloud file, opened it in Ekahau, saved it as-is → the resulting file was 1.5 MB. Byte-for-byte inspection confirmed: Ekahau Cloud stores `.esx` entries **uncompressed** (ZIP "stored" mode), while local desktop Ekahau **deflates** them. The two files had byte-identical floorplan images and near-identical JSON payloads — same project, different container.
3. **The real "same project" signal was hiding in plain sight.** Every `.esx` has a stable UUID in `project.json.id` that Ekahau assigns at creation and preserves through every edit, rename, upload, and download. Both files had `redacted-cloud-id`. Same project, provably.

## The fix — five-pass matching hierarchy, strongest-evidence-first

`build_matches` now runs five ordered passes. Each pass consumes matches greedily so no weaker pass can steal a local `.esx` from a stronger claimant later in the pipeline.

| Pass | Signal | Auto? | UI badge |
|---|---|---|---|
| **−1** | **Manual pair** — user said "these two ARE the same" | Always, overrides everything | ★ **You matched** (purple) |
| **0** | **Same `project.json.id` UUID** | Definitive | ✓ **Exact same** (green) |
| **1** | **Exact name equality** | High confidence | ✓ **Same name** (blue) |
| **2** | **Same site code + fuzzy name**, discriminator check | Medium | ~ **Same site** (amber) |
| **3** | **Fuzzy name only**, discriminator check | Guess — surfaced as such | ? **Similar name** (grey) |

Pass 0 alone would have solved the maintainer's original case. Passes 2 and 3 still use the discriminator guard (Bldg 3 vs Bldg 5, or Baseline vs Cleanroom-PD, are semantically different regardless of anything else). But `_size_conflict` and `_mtime_conflict` are gone — see below.

## What we retired (and why)

**`_size_conflict` — deleted.** Cloud is stored uncompressed, local is deflated. Same project can legitimately show up as 5–10× different on disk. No ratio threshold saves that; the whole guard was solving a problem that doesn't exist in this domain.

**`_mtime_conflict` — deleted.** Cloud mtime = "when last edited on Ekahau server." Local mtime = "when last written to disk after download." These legitimately drift by years for the same project. Not a reliable "not the same" signal — Pass 0 (id) covers the real case, and manual pair (Pass −1) is the escape hatch for edge cases.

**`pair_conflicts` collapses to just `discriminators_conflict`.** Semantic name-based checks are the only guards left, and those only apply to Passes 2 and 3 (Passes −1, 0, and 1 override them).

## Held Back — the pairs auto-matching rejected, now visible with reasons

Pass 2 and Pass 3 discriminator rejections used to silently drop into two separate orphan rows. Users had no way to know that WD had *considered* a pair and rejected it, let alone why. Now they land in a **Held Back** collapsible section at the bottom of the ledger, one row per rejection, each with:

- The two file names side by side (CLOUD ↔ LOCAL badges)
- A plain-English reason: *"Building numbers don't match (3 vs 5)"* / *"Street numbers don't match (17020 vs 27042)"* / *"Survey phases don't match (baseline vs postinstall)"*
- **[Link anyway]** — pairs them via the manual-match store, remembered forever
- **[Not a match]** — records the pair as never-suggest, mirrors the existing not-match store

The section persists open/closed state in localStorage. Owner filter (Mine/Others) applies.

## Manual pair — user override, remembered forever

Every orphan row on the projects tab has a new 🔗 button in the middle gutter next to the primary upload/download arrow. Clicking it opens a **Link Picker** modal with a searchable list of counterparts from the opposite side. Same-site-code candidates are surfaced above others so the obvious pair is one click away.

- **Backend**: `MANUAL_MATCH_FILE` at `~/.wd_wireless_tools/manual_matches.json`, same shape as the existing not-match store.
- **`mark_manual_match`** auto-clears any conflicting not-a-match record so the two lists can't contradict each other.
- **The ★ "You matched" badge is clickable** — click it on any manually-paired row to prompt "unlink and go back to auto-matching."

## Row meta: size dropped, date+time added, sourced from inside the file

Row metadata used to show file size in bytes. Given that cloud/local sizes are apples-to-oranges (per above), showing them on rows was actively misleading. New format:

- Old: `9.2 MB`
- New: `Jul 27, 5:53 PM` (this year) / `Jul 27, 2025, 5:53 PM` (older)

Dates are now sourced from `project.json.history.modifiedAt` inside the `.esx`, not from the filesystem mtime. Rationale:

- **Filesystem mtime resets on copy, OneDrive sync, Windows-touch, and re-save.** Two identical copies of the same project can have wildly different filesystem mtimes.
- **Internal `history.modifiedAt` is baked in when Ekahau saves.** It survives all of the above and, crucially, is directly comparable to the cloud's `history.modifiedAt` (both come from the same Ekahau save event).
- **Two files with the same internal date+time down to the minute are the same snapshot, byte-for-byte** (minus the compression wrapper). That's a strong at-a-glance signal for "these are literally the same save."

Size is still on the underlying data — folder-peek popup and Duplicates tab still show it because those views compare files of the same kind, where size IS meaningful.

## Confidence badges — every paired row now says WHY

The middle gutter used to show `=` on synced pairs and `≠` on mismatches. Now every paired row shows a colored pill with the match reason:

- Text-on-color instead of an unlabeled glyph, so it reads without needing to learn a legend
- Hover tooltip carries the plain-English explanation for anyone new to the tool
- Color hierarchy: green (id) → blue (name) → amber (code) → grey (fuzzy) → purple (manual)
- Full theme support (both dark and light modes tuned separately for WCAG)

## Help chip + first-visit hint + user manual section

Small **ⓘ How matching works** chip next to the toolbar search opens a modal with the full explanation, including a visual guide to all five badge types. First-time visitors see a dismissible banner: *"Matching is smarter now. WD uses a hidden project ID inside each `.esx` to know when two files are the same — not file size (which is misleading across cloud/local)."* Same copy also lives in the Cloud Manager user guide under a new **How Matching Works** section, so both in-app and out-of-app documentation cover it.

## Files changed

**Backend (`tools/cloud_manager.py`):**
- New `_esx_meta(path, mtime)` reads `project.json` once and returns `{author, projectId, internalMtime}`; back-compat shim `_esx_author` delegates to it.
- `get_local_esx_files` now attaches `projectId` and uses internal mtime for display.
- `build_matches` rewritten: Pass −1 (manual), Pass 0 (id), Pass 1 (exact), Pass 2 (code), Pass 3 (fuzzy), plus `heldBack` capture on Pass 2/3 discriminator rejections. Signature grows a `manual_map` parameter.
- `discriminators_reason(a, b)` — returns plain-English reason string or None; `discriminators_conflict` becomes a thin wrapper.
- `pair_conflicts` collapses to just discriminators; `_size_conflict`, `_mtime_conflict`, `_SIZE_FLOOR_BYTES`, `_SIZE_RATIO_CUTOFF`, `_MTIME_GAP_SECS` all removed.
- New manual-match persistence: `MANUAL_MATCH_FILE`, `load_manual_matches`, `save_manual_matches`, `manual_matches_map`. New `CloudManager` methods `mark_manual_match`, `unmark_manual_match`, `list_manual_matches` mirror the not-match ones.
- `_fmt_short_datetime` replaces `_fmt_short_date` (adds time-of-day); `_row_meta` drops size.

**Server (`server.py`):**
- Three new endpoints: `mark_manual_match`, `unmark_manual_match`, `list_manual_matches`.

**Frontend (`web/assets/js/cloud.js`):**

- `openLinkPicker` + `_lpFilter` + `_lpPick` drive the new manual-pair picker modal; `_collectOrphansOfKind` gathers candidates.
- `markManualMatch` / `unmarkManualMatch` handlers + API_MAP entries.
- `openMatchHelp` / `_mhInit` handle the help chip and first-visit hint.
