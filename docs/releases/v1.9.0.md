Cloud Manager's file operations got a wholesale UX rethink. Instead of a stack of one-off modals — `#workingModal` for downloads, `#progressModal` for bulk sync, individual toasts for renames/moves/deletes — every file op now flows through a **single unified surface**: the **Operations Deck**.

The Deck is a persistent, collapsible drawer anchored to the bottom-right of the app. It appears the moment any file op starts. Every operation gets its own **card** with a title, a real progress bar, a status icon, and — where the op is reversible — a **60-second Undo button**. When ops fail, the card shows the error inline with a **Retry button**. When something's running you don't want anymore, there's a **Cancel button**. When you've seen enough, one click hides the deck.

Also included: **Cloud Only count bug fix** — the dashboard counter now respects the Owner filter (Mine / Others / All), matching what the row list actually shows.

Suite `v1.8.46 → v1.9.0`. WD Cloud Manager `v3.49 → v4.0`.

## What changed

### The Operations Deck

**Anchored to the bottom-right corner**, 560px wide (or `100vw - 40px` on narrow screens), floats above the app content on `z-index: 90` (below modals, above the toolbar). Its state is one of three:

- **Hidden** — no ops in flight or completed, nothing showing. Auto-appears on first enqueue.
- **Expanded** — full body with all op cards visible, scrollable when >4-5 cards.
- **Collapsed** — thin header bar only, showing the summary count. Click header to expand.

**Header shows the summary at a glance:**

```
[◈] 2 running · 1 queued · ✓ 5 · ⚠ 1    [Clear done] [▲] [×]
```

Counts flip live as ops progress. **Clear done** removes all completed/failed/cancelled cards but leaves running ops alone. **×** hides the deck entirely (it'll pop back on the next op).

**Each op card:**

```
┌─────────────────────────────────────────────────────────┐
│ ↻  Downloading "sample-project.esx"        [Cancel]     │
│    Floor plan 3/8                                        │
│    ▓▓▓▓▓▓░░░░░░░░░░░░░░░░  37%                          │
└─────────────────────────────────────────────────────────┘
```

Status icons and colors tell the story at a glance:
- **↻ blue spinner** — running
- **⏸ grey dashed border** — queued
- **✓ green** — done
- **⚠ red border, red icon** — failed (with inline error message + Retry)
- **⊘ grey, faded** — cancelled

**Actions appear contextually:**
- **Cancel** — only shown while running, only when the op opted in (uploads/downloads support cancel; instant ops like assigns don't bother)
- **Retry** — shown on failed ops that have a `retryFn`
- **Undo `55s`** — shown on completed reversible ops, with the seconds counting down. When the 60s window expires, the button fades away and the card stays another few seconds before auto-clearing.
- **×** — dismiss the card

### What flows through the Deck

**Everything file-op:**

| Operation | Type | Progress? | Undoable? | Cancelable? |
|-----------|------|-----------|-----------|-------------|
| Download (single & bulk) | `download` | ✓ real, per-image | — (file's on disk) | ✓ |
| Upload (single & bulk) | `upload` | ✓ real, staged | — (would delete cloud copy) | ✓ |
| Move to Site (single & bulk) | `move` | — (fast) | ✓ moves back | — |
| Rename cloud/local | `rename` | — (fast) | ✓ renames back | — |
| Delete cloud/local (single & bulk) | `delete` | — (fast) | — (no restore API) | — |
| Undo of any of the above | `undo` | — (mirrors original) | — (no undo-of-undo) | — |

Backend progress plumbing (from v1.8.45) is preserved — downloads still emit real per-image progress via `/api/cloud/progress?id=<opId>`, uploads emit stage progress. Ops that don't need backend polling (moves, renames, deletes) set `pollBackend: false` and just show a "running" state until the API call returns.

### Undo semantics

Every reversible op captures its **inverse** as an `undoFn` at enqueue time:

- **Move to Site (cloud project)**: undo re-assigns the project to whatever site it was on before (or unassigns it if it had none). `t.prevSiteId` is captured from `rowData` at enqueue time.
- **Move to Site (local .esx)**: undo moves the file back to its original parent folder. The original path is derived from the source path before the move happens.
- **Rename (cloud)**: undo renames back to the old name. Requires `oldName` to be captured — if we can't find it, the op is enqueued as non-undoable.
- **Rename (local)**: undo constructs the post-rename path (`parent + newName + .esx`) and calls `rename_local` with the old name.

Clicking Undo enqueues a **new op** (titled `Undo: <original>`) so you can see the reversal execute. There's no undo-of-undo — the original op's `undoFn` is cleared once used.

**Not undoable by design:**
- **Uploads** — the undo would delete the just-uploaded cloud project. Too destructive for a 60s window; do it manually if needed.
- **Downloads** — the downloaded file is on disk. If you want it gone, delete it from the local side.
- **Deletes** — backend has no restore API. Once gone, gone.

### Cancel semantics

- **Non-forceful.** The op's `run` function receives a `cancelFlag` object; it checks `cancelFlag.aborted` at natural checkpoints. Some ops (like a single blocking HTTP request) can't be interrupted mid-flight; they'll finish before the cancel takes effect. That's fine — the card shows "Cancelling…" until the current request resolves, then flips to cancelled.
- **Deck cards for cancelled ops** stay visible for a moment so you can see what happened, then auto-clear.

### Retry semantics

Failed ops that were given a `retryFn` at enqueue time show a Retry button. Clicking it **removes the failed card** and **enqueues a fresh op** using the retry function. Uploads and downloads currently retry with the same source/target; delete retries the same delete.

### Cloud Only count bug fix

Before: dashboard showed `Cloud Only: 3` while the row list was empty because Owner=Mine was hiding all three (they were owned by `teammate-a@example.com`).

After: `updateDashboard()` applies the same `_passOwnerForCounts(cloudObj, localObj)` predicate the row renderer uses. When you switch Mine/Others/All in the owner toggle, both the dashboard counts and the row list update together — always consistent.

Fields fixed: All, Mismatches, Orphans, Cloud Only, Local Only, Synced, No Site. Behaves identically on the Sites tab (Owner filter doesn't apply there → no-op).

## Design decisions

**Why a deck instead of a modal?** Modals block. When you're managing 30 projects across 15 sites, you're running many ops interleaved — checking downloads while queuing uploads while renaming a couple of sites. A modal forces one-at-a-time; the deck accepts all of them at once and shows them in parallel. It also stays out of your way — you can keep clicking around the app while ops run.

**Why bottom-right instead of top or side?** Bottom-right is the OS-native corner for status/notifications on both macOS and Windows. It's where notifications appear, where the system tray lives — muscle memory. The deck opens toward the user's dominant focus (top-left of the deck is where new ops appear, closest to the app content above).

**Why 60 seconds of undo?** Long enough to catch "wait, that was the wrong site" thinking; short enough that the undoFn can safely go stale without ambiguity (e.g. a move-back after 10 minutes might collide with newer state). Matches macOS Finder's undo window for delete-to-trash operations.

**Why is Delete not undoable?** The backend has no restore. Adding a soft-delete/trash layer to `cm.delete_local` and `cm.delete_cloud` is a real feature, not a wrapper, and belongs in its own release.

**Why keep the old `#workingModal` and `#progressModal` HTML around?** Belt and suspenders — if any legacy code path still calls `showModal('workingModal')`, it fails silently rather than blowing up. They can be removed in a later cleanup once the migration is confirmed complete.

## Verification

1. **Deck appears/hides:** Open Cloud Manager → deck should be hidden. Click ↪ **Move to Site** on any orphan row → deck slides in from bottom-right.
2. **Progress bar moves:** Click red ⮕ on a cloud-only row → confirm the download → watch the bar fill as image chunks arrive.
3. **Bulk mode:** Tick 3 cloud-only rows → **Sync →** in the toolbar → three separate deck cards appear, each with its own progress bar.
4. **Undo works:** Move any local file to a site → wait for done → click **Undo** → new "Undo: Moving…" card appears → file moves back.
5. **Retry works:** Cause a failure (e.g. delete a cloud project you don't have permission to touch) → click **Retry** → same op re-runs.
6. **Cancel works:** Start a big download → click **Cancel** → status flips to Cancelling…, then Cancelled once the current step ends.
7. **Clear done:** Complete several ops → click **Clear done** in the deck header → done/failed/cancelled cards vanish, running ones stay.
8. **Hide/reveal:** Click **×** on the deck header → deck slides away. Trigger any file op → deck slides back with the new op.
9. **Count bug fix:** Projects tab → toggle Owner: All / Mine / Others → dashboard counters shift with the row list every time. No more "Cloud Only: 3" while rows show 0.
10. **Collapsed state:** Click the deck header caret → deck collapses to a thin bar showing just the summary. Click again to expand.

## Files changed

**Frontend:**

- `web/assets/js/cloud.js` — big rewrite of the file-op UX layer:
  - New Operations Deck engine: `_ops` map + `_opOrder` array, `_deckRender()`, `_opCardHtml()`, `_opIcon()`, `_opActionsHtml()`, `_deckToggle()`, `_deckHide()`, `_deckClearDone()`, `_opRemove()`, `_ensureDeckTick()`, `_ensureDeckPoll()`.
  - Public API: `opEnqueue({title, sub, type, undoable, undoFn, retryFn, pollBackend, cancelable, run})` returns `{id, promise}`. `opCancel(id)`, `opUndo(id)`, `opRetry(id)`.
  - `runWithProgress(opts, fn)` retained as a thin compatibility shim over `opEnqueue` — no callers changed, but the fullscreen modal is gone.
  - Migrated `bulkSync` to enqueue per-item ops (rename / upload / download) instead of populating `#progressModal`.
  - Migrated `confirmDelete` (single + bulk) to enqueue delete ops with retry.
  - Migrated `confirmRename` and `syncRow` to enqueue rename ops with undo.
  - Migrated `confirmMoveToSite` per-target loop to enqueue move ops with undo (both `assign_to_site` and `move_local_to_site` paths).
  - Owner-filter fix: new `_passOwnerForCounts(cloudObj, localObj)` predicate; `updateDashboard()` recomputes counts through it. `setOwnerFilterUI()` now calls `updateDashboard()` in addition to `renderRows()`.
  - Removed dead helpers: `openBulkProgress`, `updateBulkProgress`, `finishBulkProgress`, `_setProgressFill`, `_setProgressText`, `_bulkAbort`. Left `cancelBulkProgress` as a no-op stub for any legacy DOM handler that hasn't been swept yet.

- `web/cloud.html` — new `#opsDeck` element (header + body containers), positioned just before `#toasts`. Version chip `v3.49 → v4.0` in both the header and About modal. Old `#workingModal` and `#progressModal` HTML kept as hidden fallbacks (see design decision above).

- `web/assets/wd-tools.css` — new **OPERATIONS DECK** section (~200 lines): `.ops-deck` container with slide-up/hide transitions, `.ops-deck-header` with the summary bar, `.ops-deck-body` scrollable list, `.op-card` grid layout with status-specific borders (`status-running` blue, `status-done` faded, `status-failed` red, `status-cancelled` grey, `status-queued` dashed), `.op-icon` with a `spin` animation for running ops, `.op-bar` + `.op-bar-fill` with an indeterminate striped mode using `op-bar-slide` keyframes, `.op-actions` with `.op-btn` variants (`primary` blue for Retry/Undo, `danger` red), `.op-undo-timer` monospace countdown.

- `web/pages/hosted-index.html` — version chip `v1.8.46 → v1.9.0`.

## What's next (deferred to a later release)

- **Drag-and-drop between the ledger and the deck** — drag a row onto the deck to enqueue a default op (delete, sync, etc.). Nice, but the current click-to-enqueue is already ergonomic.
- **Cart mode** — pre-stage multiple targets, review, then Execute All. Different mental model from the current tick-and-act flow; would live as an opt-in.
- **Soft delete / trash** — backend layer needed so deletes could join the undoable set. Its own feature.
- **Ops history persistence** — currently the deck only shows the current session. A "history" panel showing what happened over the last few days could be nice, but tricky (some ops mutate state that has drifted).
