The **Sites** tab used to be a flat, alphabetically-sorted list of cloud sites ↔ local folders — you had to click a peek icon to see which projects lived inside a site. It's now a real Windows-Explorer-style tree: each site expands to show its own projects, matched cloud ↔ local, in the exact same two-column layout the Sites tab has always used. Cloud projects that don't belong to any site at all (nothing to nest them under) are grouped in an **Orphan Projects** section at the bottom.

```
Alpha Site
    sample-project.esx        (synced)
    sample-project.esx    (cloud only)
Beta Site
    sample-project.esx         (mismatch — click ➡/⬅ to sync the name)
⚠ Orphan Projects — no site (1)
    sample-project.esx
```

Suite `v1.9.5 → v1.9.6`. WD Cloud Manager `v4.0.5 → v4.1.0`.

## What changed

### 1 · Backend: sites carry their own project matches

`build_sites_data()` now nests a full `children` match-set (matched/mismatches/cloudOnly/localOnly — the same shape the Project Files tab already uses) under every site and local folder, scoped to just that site's cloud datasets vs. that folder's local `.esx` files. It also returns a top-level `orphans` list: cloud projects that aren't assigned to any site, which is the one case that can't nest anywhere in the tree.

### 2 · Frontend: expandable tree, same two-column ledger

The Sites tab gained a dedicated `renderSitesTree()` renderer. Each site/folder row gets a `▶` chevron (click to expand/collapse — sites start expanded so a large scope is visible at a glance) and its child projects render directly beneath it, indented on both the cloud and local columns, using the identical `cloudCell`/`gutCell`/`localCell` row templates as the rest of the app. Orphan projects get their own divider section at the bottom with the same row layout, plus a "Move to a site" button to fix them on the spot.

Because project rows can now render while the active tab is still "sites," the single-row rename/delete/sync actions (`startRename`, `startDelete`, `syncRow`) needed to stop inferring "am I renaming a site or a project?" from the current tab and instead take an explicit `kind` argument — otherwise a nested project row would have called the site-rename/site-delete API on a project id.

### 3 · Nothing about the flat Project Files tab changed

The Project Files tab (flat, ungrouped project list) and Duplicate Projects tab are untouched — this is purely a Sites-tab rendering change plus the backend data it now carries.

### 4 · Known gap vs. v1.9.5's "download lands in site folder"

v1.9.5 taught `downloadThenMove()` to skip the Move-to-Site prompt when a cloud project's site is known, by looking up `siteName` on the row via `rowData['c:'+id]` / `rowData['p:'+id]`. Project rows nested inside the new Sites tree use different row keys (`ct:`/`op:` prefixes, since they're children of a site row, not top-level rows), so that lookup misses for them today — clicking download on a project inside the tree falls back to the old "pick a site" prompt instead of auto-landing in the site it's already nested under. Not a regression (nothing breaks), just an optimization that doesn't reach the new tree yet. Worth wiring up in a follow-up.
