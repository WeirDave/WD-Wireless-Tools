# Cloud Manager: a project changed on both sides is no longer overwritten, and transfers no longer replace work saved in the meantime

Suite **2.239.0**. Cloud Manager **4.92.0**. Other tools are unchanged.

## What changed

### Cloud Manager: replacing the cloud copy with a local file

Applies to **Local newer · replace cloud** on a row, and to **Sync everything** and **Sync selected** when they send local files up.

- **A cloud project that changed since the two were last the same is no longer deleted without a question.** When the cloud copy has been edited since this computer last had both sides identical, a dialog titled *Replace a cloud copy that has changed?* names the project and what is lost. **Replace the cloud copy** continues; closing the dialog leaves both sides untouched. The check is made by the server at the moment of the replace, so a list that was drawn earlier cannot skip it. A project this computer has no sync record for is not asked about.
- **The old cloud project is deleted only after the uploaded copy has been downloaded back successfully.** Previously a failed read-back was reported as a warning and the old project was deleted anyway. Now both copies are kept, and the message names which is which and what to do next.
- **A file that is missing survey samples asks before replacing the cloud project, on every route.** The dialog *Replace the cloud copy with a file missing survey data?* previously appeared only for a single row. **Sync everything** and **Sync selected** now ask as well, per file, with **Replace it anyway** to continue.
- **A file that is not a complete project is not uploaded.** A truncated archive, or one with no project record (for example while Ekahau or a sync client is still writing it), is refused before anything is sent.
- **A file saved while the upload is running is not overwritten by the cloud copy.** The upload still counts as read back; the local file is left as it is and the result says so.
- **A failed write of the cloud copy over the local file no longer leaves a full-size temporary file behind.**

### Cloud Manager: downloading the cloud copy over a local file

Applies to the **Download over local** arrow on a row, **Verify** on name-matched pairs, and the download steps of **Sync everything** and **Sync selected**.

- **A pair edited on both sides is refused.** When the local file and the cloud copy have both changed since they were last the same, the download is skipped with a message saying so and that nothing was changed. The refusal is lifted when a content comparison shows the cloud copy holds the same design. In bulk runs the pair is counted as skipped.
- **A local file saved while the cloud copy is downloading is left alone.** The file is re-checked immediately before it is replaced.

### Cloud Manager: deleting local files and folders

- **A folder that could only be partly deleted is reported as such.** A file held open by another program previously left the call answering success over a folder that still held it, and the merge step *Delete the source folder afterward* trusted that answer. The message now gives the number of files remaining.
- **The folder that holds all sites cannot be deleted or renamed from Cloud Manager.**
- **The delete dialogs state what a folder holds.** The single-folder dialog gains a line giving the number of `.esx` projects in the folder, which were previously not counted. In the bulk dialog each local folder shows its contents (for example *3 .esx projects, 2 other files*).

### Cloud Manager: matching local files with cloud projects

- **A manual link applies to the file it was made on.** If that file is deleted and a different project is downloaded to the same path, the old link no longer pairs the new file with the old project.
- **Manual links are one-to-one.** Linking a cloud project again replaces its earlier link, and a file can belong to only one link. Removing the newest link no longer brings an older one back.
- **Two projects with the same name pair with the folder of their own site, regardless of the order Ekahau lists them in.**
- **Of several local copies of one project, the most recently saved is the paired one.** An older copy in another folder no longer hides edits made to the newer one.
- **Names that differ only in how an accent is stored are treated as the same name.**
- **Sync records are kept when a listing looks wrong.** An empty project list from Ekahau no longer clears the records that identify a pair as changed on both sides, and a record for a project missing from the list is kept for 30 days.

### Cloud Manager: Duplicates tab

- **The paired flag uses the same rules as the Projects tab:** project ids, manual links and pairs marked *Not a match*. The project the local file actually belongs to is no longer offered as the extra copy.
- **Files with the same name but different projects are no longer grouped as duplicates.** Copies of one project still are.

### Cloud Manager: merging folders

- **Keep newer compares the date saved inside each `.esx`,** not the file system date, which changes when a file is copied or synced. An older project that was touched later no longer replaces newer work.
- **Overwriting a file during a merge no longer removes the destination first.** The incoming file is placed beside it and swapped in, so a failed move leaves the existing file in place.

## Known limits

- A content comparison treats a difference in project-level settings, the version file or the edit history as not changing the design. A pull refused because a local file looks newer can therefore still proceed when only those differ.
- The Sites tab pairs files within each paired site folder only, so a link or id match to a file in a different folder appears on the Projects tab rather than the Sites tab.
- A pair marked *Not a match* is still paired when the local file carries the cloud project's own id, because that id is Ekahau's record that they are the same project.

## Verified

- Each new guard has tests that fail when the guard is disabled: a pull and a push on a pair changed on both sides, a download and an upload during which the local file is saved, a replace whose read-back fails, a file missing survey samples, a partial folder delete, a merge deciding by file date, a stale manual link, and sync records after an empty list.
- The full suite passes.
