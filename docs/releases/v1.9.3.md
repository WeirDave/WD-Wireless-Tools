The original problem the Operations Deck was built to solve: **cloud transfers were opaque** — downloading or uploading a `.esx` was a 10–30 second black box with no feedback. That's what the deck fixes.

In v1.9.0 I over-generalized and routed **every** file operation through the deck, including instant local ops like rename and delete. the maintainer — correctly — pointed out that's noise: *"If I click 3 files in File Explorer and hit delete, I don't get a popup telling me they're deleted. I selected them, I know."*

Refocused. The deck is now scoped to what it was originally for:

- **Deck shows:** uploads and downloads. Real progress bars, per-item cards, retry on failure. Single or bulk.
- **Deck does not show:** renames, deletes, moves, or any op that doesn't cross the local↔cloud boundary. Those are toast + auto-refresh. Silent success, error toast on failure.

Suite `v1.9.2 → v1.9.3`. WD Cloud Manager `v4.0.2 → v4.0.3`.

## What changed

### The refocus

Five call sites reverted from deck-op enqueue to direct `pyApi + toast + _scheduleOpRefresh()`:

| Op | v1.9.2 (before) | v1.9.3 (now) |
|-----|-----------------|--------------|
| Rename via ✎ pencil | Deck card + undo | Toast + refresh |
| Rename via ↓ arrow (per-row) | Deck card + undo | Toast + refresh |
| Bulk rename via Sync → / Sync ← (matched pairs) | N deck cards + undo | Loop + summary toast |
| Delete (single) | Deck card | Toast + refresh |
| Delete (bulk) | N deck cards | Loop + summary toast |
| Move to Site (single) | Deck card + undo | Toast + refresh |
| Move to Site (bulk) | N deck cards + undo | Loop + summary toast |
| **Upload (single via ← arrow)** | Deck card | **Deck card** (unchanged — slow) |
| **Upload (bulk via Sync ←)** | N deck cards | **N deck cards** (unchanged — slow) |
| **Download (single via → arrow)** | Deck card | **Deck card** (unchanged — slow) |
| **Download (bulk via Sync →)** | N deck cards | **N deck cards** (unchanged — slow) |

### Bulk toast summary shape

When you Sync-rename 5 files: single toast `Renamed 5 files`. If two fail: `Renamed 3 · 2 failed (first error message)`. Same shape for Delete and Move.

### Why the deck still works for cloud transfers

Uploads and downloads take real time (2 seconds to 2 minutes depending on `.esx` size). The whole reason the deck exists is to give you a visible progress bar during that window instead of a blank screen. Nothing changed about that path — single arrow-triggered uploads/downloads AND bulk Sync-triggered ones both still enqueue into the deck with their per-item progress bars.

### Backlog captured

the maintainer asked about **batch pattern rename** (add a prefix, replace a substring across N filenames). That's a real feature — not on this release, but it's on the backlog. Would live as a "Rename pattern…" toolbar button when 2+ rows are ticked, opening a small dialog with prefix/suffix/find-replace/preview.
