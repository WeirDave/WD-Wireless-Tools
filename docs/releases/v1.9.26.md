WD Cloud Manager — A-Z jump nav actually scrolls now.

Suite `v1.9.25 → v1.9.26`. WD Cloud Manager `v4.6.1 → v4.6.2`.

## The bug the maintainer hit

Clicked **U** in the shiny new jump-nav. Ledger stayed put with **S** at the top. Not a subtle miss — no scroll happened at all.

## Root cause

`scrollIntoView({ behavior: 'smooth', block: 'start' })` doesn't reliably propagate through nested scroll containers in Chrome. The Cloud Manager's rows scroll inside a `.rows-container` with `overflow-y: auto` (not the window), and Chrome quietly no-ops the smooth-scroll call on it — `scrollTop` stayed 0 no matter how far down the target was.

I patched that with a manual walk to find the scrollable ancestor and drive it with `scrollEl.scrollTo({ top, behavior: 'smooth' })`. **Also didn't work** — proven by intercepting `scrollTop` before/after: still 0.

Then I added `scroll-behavior: smooth` to `.rows-container` CSS as a fallback. That *broke direct assignment too* — `scrollEl.scrollTop = X` immediately snaps back to 0 when the smooth-behavior CSS is present but the browser can't animate for some reason. The container is "smooth-locked" without actually scrolling.

## The fix

- Ditched smooth entirely for the jump. Direct `scrollEl.scrollTop = offset` — instant, unambiguous.
- Removed the `scroll-behavior: smooth` from the container CSS (it was the actual blocker).
- Kept the manual scrollable-ancestor walk since it correctly resolves to `.rows-container`, not the window.

Instant is honest for a jump — the user's mental model is "take me there," not "gently glide me over." If we want smooth later, a requestAnimationFrame tween is trivial to add.

## Verified in the preview

Fired `_jumpToLetter` on U, W, A in sequence, read `.rows-container.scrollTop` after each:
- After U: 7616 ✓
- After W: 7988 (further down than U, matching W's position after U alphabetically) ✓
- Jump-flash animation on the target header still fires as before.
