WD Cloud Manager — download-then-move now uses the parent site as the destination when the cloud row is a tree-child, and the Move-to-Site picker no longer proposes the folder we literally just created.

Suite `v1.9.22 → v1.9.23`. WD Cloud Manager `v4.5.4 → v4.5.5`.

## The bug the maintainer hit

Cloud project `SITE-001 E - Trouble Call Survey` was sitting inside the SITE-001 site in the tree — cloud-only, no matching local `.esx` yet. the maintainer clicked the red ← arrow to download it, expecting the file to land inside the SITE-001 local folder that already exists.

Instead:
1. Download landed in a brand-new folder named after the project (`SITE-001 E - Trouble Call Survey`) at the top level of his Ekahau Projects directory.
2. Move-to-Site picker opened with an auto-suggested destination.
3. the maintainer accepted the default (assumed WD had picked the right thing) → nothing moved, and the new orphan folder stayed.

## Two independent bugs, one path

**Bug 1 — `downloadThenMove` didn't look at `ct:` rowData keys.** When a cloud-only project sits under a site as a tree-child (either Ekahau-assigned or paired via WD's cross-tree matching), it's indexed in `rowData` under `ct:<cloudId>` — but the download-target lookup only checked `c:<cloudId>` and `p:<cloudId>`. Result: `siteName` came back empty even though the tree row clearly knew what site the project belonged to, so the download fell through to the "pick a site" fallback.

**Bug 2 — `_suggestSiteFor` proposed the just-created folder as the destination.** Pass 1 of the auto-suggest scans the file's parent folder and checks whether any known site matches that folder's name. When `downloadThenMove` fell into the fallback and created a new folder named after the project, that new folder became a site in the ledger (because `get_local_folders` picks up every top-level directory). Pass 1 then found it, marked it as an auto-suggested destination with score 2.0 (highest priority), and the picker pre-populated with a suggestion that was semantically "move this file to itself."

## The fixes

**Fix 1 — `downloadThenMove` now checks the `ct:` key first.** New lookup order: `ct:<id>` → `c:<id>` → `p:<id>`. When the project is a tree-child under a site, the `ct:` entry has `siteName` set to the parent site's name (from the `indexChildren` walk added in v1.9.18), so we resolve the correct destination without a picker.

**Fix 2 — `_suggestSiteFor` skips parent-folder Pass 1 when the folder name matches the file name.** A folder named the same as the file inside it is the signature of a just-created orphan; auto-suggesting it back to the user is worse than showing no suggestion at all. Pass 2/3 (fuzzy name score) still runs, so if a legitimate site fuzzy-matches, it still surfaces.

## Verified in the preview

Intercepted the `download_project` API call for a tree-child cloud row and confirmed:

- Old behavior: `folder: "SITE-001 E - Trouble Call Survey"` (project name → new folder)
- New behavior: `folder: "SITE-001 - 1400 Example Corp, Springfield, CA 90001"` (parent site → existing folder) ✓
- `confirm()` prompt was intercepted-accepted; picker never opened (skipPicker=true).
