*"Couldn't reach GitHub?"* — Dave, from the About modal on a perfectly working install.

He wasn't offline. GitHub was rate-limiting his IP. The About modal's *Check for updates* hits `api.github.com/repos/…/releases/latest`, and GitHub caps unauthenticated calls at 60/hour per IP. If you burn through that quota — shared IP, kicking tires, opening About a few times a day — every subsequent check returns `403 rate limit exceeded`, and the modal previously collapsed all failures into a single scary line: **"Couldn't reach GitHub."**

That's a bad UI on two counts. First, it reads like the install is broken when it isn't. Second, it invites tickets for nothing.

**Fix.** The updater now distinguishes rate-limit responses from real network errors and tells the truth:

- **Rate-limited.** *"GitHub's update check is temporarily rate-limited (retry in ~12 min). Not a problem with your install."* — the minute count comes from the `X-RateLimit-Reset` header GitHub returns with every 403.
- **Actual network failure.** *"Couldn't reach GitHub right now — check your connection or try again in a few minutes."*

Both still link to the releases page in case you want to eyeball the latest version manually.

**Also.** Failures now cache, not just successes. A rate-limit hit is remembered until GitHub's reset time (plus a 30-second buffer); other failures cache for 30 minutes. That means opening About or reloading the page during a rate-limit window doesn't fire another doomed request — it just shows the cached friendly message. Even the force-refresh path (clicking *Check for updates* again) short-circuits if we already know we're rate-limited, so you can't accidentally spam yourself.

Small CSS polish: the suite version pill next to the home-page tagline (added in [v1.32.2](v1.32.2.md)) now gets a subtle dot separator and slightly bolder weight, so `A suite of Ekahau workflow tools · v1.32.3` reads as one line rather than a stray version floating loose.
