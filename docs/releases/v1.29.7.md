WD Wireless Tools now has its first automated safety suite: **27 passing tests** covering the local file operations and matching logic most likely to cause regressions as the project grows. The new tests use temporary directories and generated fictional ESX archives; they never touch a user's Ekahau projects, saved settings, browser cookies, or Cloud account.

The suite immediately found and locked down one real Cloud Manager matching bug: `Bldg 2` could be parsed as building `G`, causing an otherwise valid match against `Building 2` to be held back.

Suite `v1.29.6 → v1.29.7`. Cloud Manager `v4.13.0 → v4.13.1`.

## What's new

### Automated safety tests

The new `tests/` folder covers:

- Squirrel classification, custom destinations, rename rules, configuration persistence, scanning, duplicate detection, organize/undo, exclusions, overrides, collisions, flat-root operation, folder migration, and suggested grouping.
- Generated ESX summaries, referenced-image extraction, project metadata, and Design/Measured/Hybrid detection.
- Cloud/local matching precedence: manual, project-ID, exact-name, site-code, fuzzy, excluded pairs, and discriminator holdbacks.
- Cloud Manager filesystem-containment safeguards.
- Quick Walls template save, scan, delete, defaults, and path-traversal protection.
- Flask page/API routes, centralized version metadata, and JavaScript syntax.

Run the suite from the project root with:

```powershell
python -m unittest discover -s tests -v
```

### Building abbreviation matching fix

Cloud Manager's building-token expression listed `bld` before `bldg`. The regex engine could therefore accept the shorter alternative and interpret the remaining `g` as a one-letter building identifier. `SITE1 Bldg 2` and `SITE1 Building 2` then appeared to conflict as buildings `G` and `2`.

The longer `bldg` alternative is now evaluated first. A permanent regression test confirms that `Bldg 2`, `Bld 2`, and `Building 2` identify the same building while genuinely different building numbers remain conflicts.

## Safety boundaries

- Tests generate fictional ESX ZIPs at runtime; no real ESX fixture is committed.
- Every filesystem test operates inside an automatically deleted temporary directory.
- Configuration and Undo logs are redirected to temporary test state.
- Live Ekahau Cloud mutations are intentionally excluded. The suite never uploads, renames, shares, transfers, or deletes Cloud data.
