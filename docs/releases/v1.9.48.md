WD Cloud Manager — ledger's cloud-column owner display now reflects Ekahau's live current OWNER, not the immutable original creator. Fixes the stale `(owner@example.com)` label on sample-project.esx after ownership was transferred to a teammate.

Suite `v1.9.47 → v1.9.48`. WD Cloud Manager `v4.8.5 → v4.8.6`.

## the maintainer's ask

Follow-up from the v1.9.47 field test where I confirmed Ekahau's live share list says teammate-a@example.com owns sample-project.esx, but WD's ledger row was still labeled `(owner@example.com) +2 shared`. the maintainer: *"according to our back end scan it still belongs to me"* — a real bug in WD's scan, not just a display quirk.

## Root cause

Cloud project rows sourced the `owner` field from `history.createdBy`, which is **immutable** — it tracks the original creator forever, even after ownership transfer. Four places in `tools/cloud_manager.py` did this:

- `build_sites_data` per-site-datasets loop (line ~1237)
- `build_sites_data` orphan-cloud loop (line ~1329)
- `build_projects_data` main cloud loop (line ~1437)
- `build_duplicates_data` cloud-items loop (line ~1567)

## Fix

Zero extra API calls needed — Ekahau's `datasetListing` endpoint (already called by every scan) returns a `datasetUsers` list per project including the full share roster with roles. The existing code was iterating that list to compute `sharedWith` but throwing away the OWNER row. Now we capture the OWNER row too and expose it as `currentOwner` on `dataset_meta` (and a parallel `dataset_owner` dict in `build_duplicates_data`).

Every owner-assignment site now uses `dm.get("currentOwner") or created_by` — live OWNER role first, fall back to `createdBy` only when the shares data isn't available for that project (defensive; shouldn't happen in practice).

Also added `createdBy` as its own field on every cloud project record so the frontend can distinguish "created by X, owned by Y" when they differ post-transfer.

## Frontend touch — richer tooltip

`cloud.js:1991` now emits a tooltip that acknowledges both:

- **Same-user case** (typical): `Current owner (from Ekahau share list)`
- **Post-transfer case** (owner ≠ createdBy): `Current owner (from Ekahau share list). Originally created by owner@example.com.`

## Also cleaned up

The comment on `EkahauAPI.list_project_shares` said `OWNER — the project creator; can't be reassigned via API`. Now that we've captured and shipped the `/transfer-ownership` endpoint, that's out of date — updated to `the current project owner (reassignable via the /transfer-ownership endpoint; distinct from history.createdBy which is the immutable creator)`. Also added Ekahau's canonical UI labels alongside the API role names (`WRITE_SHARE_USER` = "Full access", `WRITE_USER` = "Edit rights", etc.) so future readers don't wonder why WD's labels don't match Ekahau's.
