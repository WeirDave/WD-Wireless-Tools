WD Cloud Manager — Manage Sharing modal grows a "Share with your Sharing Group" toggle, add-form no longer overflows the modal, and the Close button gets breathing room above it.

Suite `v1.9.43 → v1.9.44`. WD Cloud Manager `v4.8.1 → v4.8.2`.

## the maintainer's asks

1. Ekahau's own web UI has a "Share with My Group" toggle that adds/removes his entire "My Sharing Group" (a teammate + a teammate) from a project in one click. WD's modal didn't have it.
2. Add button in the "Share with someone" row was overflowing the right edge of the modal.
3. Close button was hugging the previous element without any padding.

## Group toggle

New row between the individual user list and the "Share with someone" add form. Shows:

- **Group name** (from Ekahau's `userGroupName` field, currently "My Sharing Group" for the maintainer)
- **Role dropdown** — View only / Can edit / Can edit & share. Disabled when the toggle is off (role only matters for active groups).
- **iOS-style toggle switch** — flip on to add the group, flip off to remove it. Uses the captured `PUT /shareapi/v1/projects/users/toggle-userGroup` endpoint.
- Changing the role while the group is active re-fires the toggle-on with the new role (that's Ekahau's own update pattern per the capture).

### The group-discovery problem

Ekahau's API doesn't have a captured endpoint that says "here's the user's sharing group id and name." That info only surfaces in `list_shares` responses as a `groupId` field on users who are members. If the group has never been enabled on a project, we don't know its id.

**Solution**: opportunistic cache. Every `list_shares` response is scanned for users with a `groupId`. First time we see one, we cache `{id, name}` to `localStorage` under `wd-sharing-group`. From that point on, the toggle renders on every subsequent modal open — even on projects where the group isn't currently active — because we know the id we'd need to send in the toggle request.

Downside: on a fresh install with a group that's never been used, the toggle won't render until the user opens a modal on a project where the group IS active (at least once). Once cached, permanent. A future "list my groups" endpoint capture would let us pre-populate the cache without needing that first-touch discovery.

## CSS fixes

- `.share-add-row` and `.share-group-row` both use `grid-template-columns: minmax(0, 1fr) 130px auto` (was `1fr 150px auto`). The `minmax(0, 1fr)` + `min-width: 0` on the input/select prevents the browser's default input min-width from pushing the trailing Add button off the modal's right edge.
- `.share-add-row .btn { padding: 7px 16px; white-space: nowrap; }` so the button doesn't wrap or shrink to nothing.
- `.modal.share-modal .modal-actions` now has `margin-top: 16px; padding-top: 12px; border-top: 1px solid var(--border);` so Close reads as its own section, not squeezed against the add-form's bottom edge.

## Verified in the preview

- Opened modal on known-shared project (the maintainer's `25bd99c7…`): group cached to localStorage with id `redacted-cloud-id`, name "My Sharing Group". Toggle rendered CHECKED (group is active on that project).
- Opened modal on a DIFFERENT project (any share button click): toggle rendered UNCHECKED, role dropdown disabled, group name displayed. Cache survived across modal opens.
- Measured: add button's right edge is inside the modal's right edge (was overflowing before).
- Close button `margin-top: 16px`, `border-top: 1px` — no more hugging.
