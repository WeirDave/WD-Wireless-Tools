WD Cloud Manager — Verify button on blue "Name matches" pairs. One click downloads the cloud copy, overwrites local, upgrades the pair to green "Same file."

Suite `v1.9.39 → v1.9.40`. WD Cloud Manager `v4.6.14 → v4.7.0` (minor bump for the new user-facing feature).

## the maintainer's design

When you create a project locally, upload to Ekahau, and later come back, the pair shows as blue **✓ Name matches** — same filename, but their internal UUIDs don't match because Ekahau's upload flow assigns a fresh cloud UUID. There's no way for the automatic matcher to prove they're the same project — but you know they are.

the maintainer's take: "instead of trying to *prove* they're the same, make them the same." Download the cloud copy, overwrite the local file byte-for-byte. Now local and cloud share the cloud's UUID, and the pair upgrades to green **✓ Same file** on next refresh.

Safe direction only in this release. Local-newer pairs get skipped with a message — that direction needs a delete+reupload flow (or an in-place update endpoint we haven't captured yet) to keep sharing/tags/version-history intact.

## What's new

- **Per-row Verify button** (green ⇩) in the middle gutter of every blue **Name matches** project pair. Click → confirm → deck card shows the download + write progress → refresh flips the badge to green.
- **Bulk Verify pairs** toolbar button. Check any set of Name-matches rows → click → one deck card per pair, processed sequentially.
- **Automatic skip when local is newer than cloud.** Backend checks internal `history.modifiedAt` (not filesystem mtime — that lies) with 60s tolerance. Local-newer pairs get a `local_newer` error and the deck card shows *"Skipped — local is newer than cloud."* No data loss possible.
- **Atomic file replace.** Backend writes to a `.wd-verify.tmp` sibling first, then `os.replace()` swaps it over — the local file is never in a half-written state.

## The mechanism

Backend `verify_replace_local(project_id, local_path)`:
1. Read local's internal `project.json.history.modifiedAt` (unreliable filesystem mtime is ignored).
2. Fetch cloud project metadata, compare `history.modifiedAt` with 60s tolerance.
3. Refuse (`error: "local_newer"`) if local is meaningfully newer.
4. Otherwise: download cloud content via existing `api.download_project` (batch + imageFiles + zip assembly).
5. Write to `<local>.wd-verify.tmp`, then `os.replace(tmp, local)`.
6. Bust `_ESX_META_CACHE` and `_ESX_TYPE_CACHE` so the next scan sees the new UUID.
7. Return the new local's `projectId` for confirmation (should equal `project_id`).

Once WD's next refresh picks up the new local content, `_esx_meta` re-parses the file, sees the cloud UUID, and Pass 0 (id-match) fires — badge goes green.
