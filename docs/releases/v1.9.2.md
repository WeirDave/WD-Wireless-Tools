the maintainer: *"After we perform an action shouldn't we just do an immediate refresh to get the live data? Waiting 30 seconds for the live tick is way too long."*

Right. Now every op that finishes in the Operations Deck triggers a **debounced 400ms auto-refresh** — the ledger updates as soon as the backend has settled, without waiting for the next Live tick. Bulk moves coalesce: 20 items finishing in quick succession fire **one** refresh, not 20.

Suite `v1.9.1 → v1.9.2`. WD Cloud Manager `v4.0.1 → v4.0.2`.

## What changed

### The auto-refresh mechanic

- New helper `_scheduleOpRefresh()` in the deck engine — starts (or resets) a 400ms timer. Each additional op that finishes within that window pushes the timer forward, so the actual refresh fires 400ms after **the last** op settles.
- Wired into all three completion paths in `opEnqueue`: `done`, `failed`, and `cancelled` all schedule a refresh. Failures still refresh so the ledger reflects any partial state changes.
- The 400ms wait also gives Ekahau's project-listing API a moment to reflect cloud-side changes (uploads/assigns propagate in 1-2s per their own polling wait, but the extra 400ms buffer is defensive against edge cases).

### Removed the ad-hoc refreshes

Previously I sprinkled `setTimeout(refreshData, 800)` in every caller (`bulkSync`, `confirmDelete`, `confirmMoveToSite`, `syncRow`, `confirmRename`). Now those are all removed — the deck's completion hook handles it centrally. Six ad-hoc call sites → one debounced mechanism.

### Verified

Instrumented test in the browser: enqueued 5 fake move ops + 1 rename op. Result: **1 refresh**. Debounce coalesces the whole burst. On real ops with network latency spread across a few seconds, the debounce will fire twice at most (once for the burst, maybe once for a lagging outlier).

### Live auto-refresh is unchanged

The 30s Live tick still runs on its own timer for background updates when nothing's happening. Post-op refreshes and Live refreshes are independent — no conflict, no double-scheduling.
