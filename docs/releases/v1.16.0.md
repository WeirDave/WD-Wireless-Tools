Squirrel now peeks inside every `.esx` it sees and shows what's in it — floor count, AP count, measurement count, survey count — right on the "staying in root" row. No more opening Ekahau to figure out which file is which.

Suite `v1.15.0 → v1.16.0`. Squirrel `v1.13 → v1.14`.

## What's new

Every `.esx` file that appears in the scan (in the "Staying in root" section) now shows a compact colored badge row underneath the filename:

- **Blue** — `2 floors` (from `floorPlans.json`)
- **Purple** — `12 APs` (from `accessPoints.json` — design APs)
- **Amber** — `3 measured` (from `accessPointMeasurements.json` — passive-survey APs picked up)
- **Green** — `1 survey` (from `surveys.json` OR the per-survey `survey-<uuid>.json` layout — both accepted, per the same fix that landed in Report v2.3)

Zero-count categories are hidden, so a bare design .esx just shows `2 floors · 12 APs` without cluttering with `0 measured` / `0 surveys`. A broken .esx (invalid ZIP, missing JSONs, etc.) silently omits the badge row rather than throwing — the file just renders without metadata.

## Cheap enough for every scan

The .esx summary is read via Python's stdlib `zipfile` — no `esxparser` dependency, no `.esx` extraction to disk. Only 3–4 JSON files are read (never the actual survey/wall data, which can be huge). Results are cached in-process by `(path, size, mtime)` so a rescan of the same folder is instant.

## Verified end-to-end

Built a synthetic `sample.esx` with 2 floors, 12 APs, 3 measurements, 1 survey. Scan API returned:

```json
{
  "name": "sample.esx",
  "esx": { "floors": 2, "aps": 12, "measurements": 3, "surveys": 1 }
}
```

Frontend rendered all 4 badges with correct token colors — `.esx-badge-floors` computed to `rgb(107, 179, 224)` = `--blue-soft`, `.esx-badge-aps` computed to `rgb(168, 85, 247)` = `--type-design`.

Broken-file test: created a `broken.esx` containing plain text (not a valid zip). Scan returned the file without an `esx` field. Frontend silently rendered the row without badges. No error surfaced.
