## What changed

### Backend: expose the site name on cloud project rows

`build_projects_data()` was already looking up each project's site via the dataset-listing endpoint to build the `meta` display string. Now it also stores the raw `siteName` as its own field on each cloud project row, alongside the existing `hasSite: bool`. Zero extra API calls.

### Frontend: `rowData` carries `siteName`

`indexRowData()` now pulls `siteName` from both `data.matched[].cloud` and `data.cloudOnly[]` into the per-row rowData entries so any code path that has a rowData key can look up the assigned site cheaply.

### Frontend: `downloadThenMove` uses the site folder as destination

The red ⮕ arrow's flow now branches on whether the cloud project has a site:

- **Site assigned:**
  - Prompt: `Download "<project>" into local folder "<site>"?`
  - Download passes the site folder name as `dest_folder_name` → backend creates the folder if it doesn't exist and lands the `.esx` inside.
  - Deck card subtitle reads `Landing in <site> — the project's site folder.`
  - Toast on completion: `Downloaded "<project>" into <site>`
  - Move-to-Site picker is **skipped** — no need to ask where it goes when we already know.

- **No site assigned:**
  - Unchanged from before: download to a per-project folder, then open Move-to-Site so the user can sort it manually.

### Frontend: bulk downloads respect siteName too

`bulkSync`'s download loop passes `d.siteName` as the destination folder when available. Each deck card's title reflects the destination — e.g. `Downloading "sample-project.esx" → SITE-001 - 100 Example Ave`. Perfect for the "download 20 projects and have them land in the right 20 folders" case the maintainer asked about earlier tonight.
