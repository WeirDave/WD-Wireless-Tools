# Cloud Manager: a renamed folder can be pushed up as its site's name, and "Make them match" asks once

Suite **2.177.0** ships **Cloud Manager 4.72.0**. The Cloud Manager page shows the Cloud Manager number, not the suite number.

## What changed

### Cloud Manager: renaming a cloud site to match a renamed local folder

- **A site row whose folder and cloud site are named differently now has a band beneath it with three controls**: **Cloud → Local**, **Local → Cloud** and **Not a match**. This band appears on the Sites tab, under the site row itself (not under the projects inside it). Before this release, site rows had no band, so there was no control that renamed a cloud site after its folder had been renamed on disk.
- **Local → Cloud** renames the cloud site to the local folder's name. The projects in the site stay where they are. It sits under the Cloud column and is the recommended action.
- **Cloud → Local** renames the local folder to the cloud site's name. The files inside it move with it. It sits under the Local column.
- **Not a match** stops the folder and the site being paired again.
- A renamed folder usually pairs with its site only by a shared site code or similar wording, because sites carry no Ekahau id. When that is how the pair was found, the band says so and asks for both names to be checked before choosing.
- **The bulk Local → Cloud on the selection bar still leaves those guessed pairs out.** Its message has always pointed to the row's own **Local → Cloud**, and on a site row that control now exists.
- Site rows whose names already agree show no band, as before. Nothing needs to be turned on.

### Cloud Manager: bulk Local → Cloud on the Projects tab

- On the **Projects** tab, the bulk **Local → Cloud** rename now leaves out projects owned by somebody else and names them in the confirm dialog, as it already did on the Sites tab. Before this release those projects were included in the run, and Ekahau refused each one with `403 Forbidden` partway through.

### Cloud Manager: the "Make them match" button in a row's detail band

- **Clicking "Make them match" on a single row now does the work straight away.** It used to download and compare the cloud copy a second time, then open a "Make these two match?" dialog with another "Make them match" button, and only then write the change. Now there is no dialog, and the cloud copy is downloaded once instead of twice.
- The button still only appears on a matched row whose comparison has already found the designs identical and whose cloud copy has the later date. It is in the row's detail band, on the local side, marked as the recommended action.
- Nothing about what gets written has changed. The cloud project's name and modified date are copied into the local `.esx`. No design content is changed, and nothing on Ekahau Cloud changes.
- The contents are still checked again immediately before anything is written. If the pair has changed since it was compared (the designs now differ, or the local copy has become the newer one), nothing is written, and a message gives the reason.
- **Making several pairs match at once works the same as before.** Selecting rows and using the bulk action still shows a preview listing every file and the edits to it, and asks before writing. Those rows may never have been compared, so the list is still the thing being agreed to.

## Verified

- New tests render a real site row whose names disagree, read each control back out of the markup and run it. **Local → Cloud** reaches the server as a rename of the cloud site to the folder name, and **Cloud → Local** as a rename of the folder to the site name. A site whose names agree still renders no band.
- New tests run the real Local → Cloud planner on rows indexed the way the page indexes them. On the Projects tab a colleague's project is left out as not the user's, the user's own project is still renamed, and a site is still treated as a site.
- New tests run the real "Make them match" handlers. The row makes exactly one call to the server, a live one rather than a preview, and opens no dialog. Bulk still makes a preview call, asks once, then makes the live call. When the server refuses at write time, its reason is shown and the action is not reported as a success.
- Each new test was confirmed to fail with the change it covers reverted.
