Cloud Manager got a wholesale file-operation UX overhaul: **real progress bars** during downloads and uploads, a **redesigned Move-to-Site dialog** that shows exactly what's moving and where it's landing, **per-item destination pickers** for bulk moves (because five selected projects don't always belong in the same site), and a **flexible auto-matcher** that recognizes both site codes (`SITE-001`) and address tokens (`100 Example Ave`) — so it works whether your naming convention is coded or not.

Suite `v1.8.44 → v1.8.45`. WD Cloud Manager `v3.47 → v3.48`.

## What changed

### The three gaps this fills

**1. File ops felt silent.** Downloading a large `.esx` from Ekahau Cloud can take 10–30 seconds — the app blocked with only a toast at the end. Same for uploads. You'd stare at nothing wondering if it hung.

**2. Move-to-Site was cramped and unclear.** The old modal was 440px wide with a single dropdown and a one-line "Project: X" header. Long filenames truncated. There was no confirmation of *what* was moving beyond that header, and no preview of *where* the file would land.

**3. Bulk moves only supported one destination.** Ticking 5 cloud projects and clicking Move-to-Site applied the same one dropdown pick to all 5 — even if three of them belonged to different sites. Users had to do sites one at a time.

### 1 — Real progress bars during file ops

A new `#workingModal` shows during any download or upload with:

- Operation title (`Downloading "B2 Predictive"`)
- Subtitle explaining what's happening
- **Old-school determinate progress bar** — filled portion in WD blue, actual percentage, stage description
- Snaps to 100% and dismisses when the operation returns

The bar moves on **real events**, not fakery:

- **Downloads:** "Fetching project data" (10%) → per-image loop with real N-of-N (up to 95%) → "Assembling .esx" → "Saving to disk" (100%)
- **Uploads:** "Requesting upload slot" (5%) → "Uploading X.X MB to Ekahau" (15%) → "Upload complete — finalizing" (85%) → "Committing" (90%) → "Waiting for cloud listing to update" (95% → 100%)

Before the backend reports its first stage, the bar shows an animated striped indeterminate state so there's always visible motion.

### How the progress plumbing works

Backend keeps a small threaded `_progress` dict keyed by `opId`. Frontend generates an opId for each operation, passes it as a POST field, and polls `GET /api/cloud/progress?id=<opId>` every 250ms while the main POST is still awaiting. Backend writes stage updates from inside `download_project` / `upload_project` into the shared dict. When the main POST resolves, the frontend stops polling. Slot is dropped on the response side to keep the dict bounded.

Waitress runs each request on its own thread, so the polling GET runs concurrently with the blocking POST that owns the operation. Lock is short-held on both sides.

### 3 — Per-item destination picker for bulk moves

When more than one item is selected, the source card becomes a table with **its own destination picker per row**. Each row shows:

- Icon + filename + size/owner
- `Into: [ picker ▼ ]` — the row's own destination
- `+ new site` inline input when the picker is set to "+ Create new site…"
- `AUTO` tag when the destination was preselected by the matcher (removed on manual override)
- Origin badge

Above the picker there's an **"Apply one site to all (optional)"** convenience — pick from the global dropdown and every row gets stamped to that site.

**Move button** is disabled while any row is unassigned. Preview line shows a rollup:

- All rows to one site: `➡ <path> — N files`
- Rows to multiple sites: `➡ N files to M different sites`
- Any unassigned: `· K still unassigned` in red

### 4 — Flexible auto-matcher

The matcher combines two heuristics and takes the higher signal:

- **Symmetric Jaccard** on word-sets — the exact algorithm from the backend's `fuzzy_similarity` in `cloud_manager.py:403`. Ports the same code so frontend and backend agree on what "similar name" means.
- **Asymmetric containment** on meaningful tokens (length > 2) — how much of the smaller token set is present in the larger. This is the new part: pure Jaccard punishes a site named `SITE-001 - 100 Example Ave, Springfield, CA 90001` when matching a file named `100 Example Ave Heatmap`, because the extra city/state/zip tokens dilute the denominator (3/10 = 0.30, below our 0.5 floor). Containment answers "does the file's tokens appear in the site name?" → 3/3 = 1.0 in that case.

**Guards against false positives** in the containment metric:

- Only tokens length > 2 count (drops "of", "ca", "at" — otherwise a shared "CA" between a California file and a Canada file would score too high)
- Requires ≥2 shared meaningful tokens — a single common word like "Predictive" or "Baseline" or "Harbor" alone can't trigger a match

**Site code bonus** — if both source and destination have an extracted site code (like `SITE-001`) and they match, add +1.0 to the score. Mirrors the backend's "code pass wins before fuzzy" priority.

**Threshold** — anything below 0.5 falls back to `— Select a site —`. No match is better than a wrong match.

Test cases (all pass):

| Source name | Best match | Why |
|-------------|-----------|-----|
| `SITE-001 - Example Ave Predictive` | SITE-001 site | code + address |
| `100 Example Ave AP Heatmap` | SITE-001 site | address only, via containment |
| `SITE-001 C-Suite Predictive` | SITE-001 site | code only |
| `SITE-001 - 400 Example Street` | SITE-001 site | code + address |
| `100 Example Ave` (bare) | SITE-001 site | pure containment |
| `Some Random Project` | (none) | no signal |
| `Predictive` / `Baseline` / `Harbor` | (none) | single common word blocked by guard |

### 5 — Merge picker uses the same matcher

The Merge folder → folder picker used to mark same-code folders with a ★ but only did exact site-code equality. Now it uses the same `_fuzzySim` + code bonus as the Move-to-Site auto-suggest, so address-based folder naming conventions also earn stars. Folders below threshold still render — the picker never hides options, only ranks them.

### 6 — Wider file-op dialogs

`.modal.file-op` at `width: min(1366px, 92vw)`. On a 1366px laptop that's the full available width; on wider monitors it caps at 1366 (never dwarfs the app). Long .esx filenames now breathe instead of truncating, and the per-item picker table has room for the site dropdown, the +new name input, and the auto tag all on one row.

### 7 — Red-arrow gutter fix, carried forward from v1.8.44

The v1.8.44 change (per-row red arrow on cloud-only Project rows) is now wired to the full download-with-progress + Move-to-Site flow. One click: confirm → progress bar during download → Move-to-Site picker with the freshly-downloaded local file pre-selected → sort into a site folder.

## Verification

1. Open Cloud Manager → **Project Files** tab
2. Filter **Cloud Only** — click the red ⮕ on any row → confirm prompt → progress bar appears with real per-image progress → Move-to-Site picker opens with the fresh file
3. Or: tick 3-5 cloud/local orphans → **Move to site…** in the toolbar → each row has its own picker → sites are auto-matched where recognizable
4. Override an auto-match: pick a different site in one row → the AUTO tag disappears → preview updates live
5. Pick "+ Create new site…" in a row → inline input appears → typed name flows into the preview
6. Try Merge (from the Sites tab, click ↪ on a folder) → the picker's ★ marks address-similar folders, not just code-similar ones
7. Upload a local orphan: click the ⬅ upload arrow → progress bar shows initiate → upload MB → commit → wait-for-listing stages
