WD Cloud Manager — Name Matches filter in Tree view now shows a *tight* filtered result: only the sites containing name-match children, and only those matching children under each site.

Suite `v1.9.61 → v1.9.62`. WD Cloud Manager `v4.9.11 → v4.9.13`.

## the maintainer's ask

> "The filter for name matches On the tree view sucks"

Two problems, both fixed.

## Problem 1: Tree children ignored the filter

`renderTreeChildren` only applied the owner filter — the `pass()` predicate that renderSitesTree used to decide site visibility was not threaded into the child render. So a site with 1 name-match child + 5 same-file children would show the site header (correctly filtered in) AND all 6 children (not filtered). Result: mostly Same file rows leaking into the "Name Matches" view.

Fix: pass the `pass` function into `renderTreeChildren` as `passFilter` and apply it to each child row before render. When the active filter is 'all', skip the extra pass to preserve the current no-filter behavior.

## Problem 2: 39 site headers for 4 project matches

Site-level exact matches (matchType='exact' on a site pair) now render as green "Same site" (per v1.9.61) — the strongest possible match for a site pair. But `rowIsNameMatch` was still treating any exact-match row as a name-match at the row level, so all 39 site pairs with `matchType='exact'` passed the filter. Result: 39 site headers wrapping 4 actual matches — 90% chrome, 10% signal.

Fix: `rowIsNameMatch` now distinguishes site rows (rows with `.children`) from leaf project rows. Leaf rows count directly. Site rows count only when they *contain* a name-match project child. That aligns the filter with the badge tier: only rows visibly labeled "Name matches" (yellow) drive the filter; rows labeled "Same site" (green, strongest) don't.

## Result

Before v1.9.62 with Name Matches filter active in Tree view:
- 39 site headers rendered (all with `matchType='exact'` at site level)
- Under each: all children rendered regardless of match state
- Actual name-match rows lost in a wall of Same-file rows

After v1.9.62:
- **4 site headers** — only the sites that contain a name-match child (SITE1, SITE-001, SITE-001, "trick folder for testing orphans")
- **4 tree-child rows** under them — every visible child is a name-match, zero Same file leakage
- Counter reads 4, badges show 4, tree shows 4

## Verified in the preview

Steps run in the browser pane:

1. Reloaded `/cloud`, version chip: `v4.9.13`.
2. Tree view (default). Click Name Matches filter card.
3. DOM inspection: `.ledger-row.tree-parent` = 4 rows, `.ledger-row.tree-child` = 4 rows. All 4 tree-child rows carry a "Name matches" badge; zero "Same file" rows appear. Counter reads 4.
4. Parent site names spot-check confirms the 4 sites make sense — each contains an unverified project pair.

## Files changed

- `web/assets/js/cloud.js`:
  - `renderLedger` — `rowIsNameMatch` rewritten with a `hasKids(row)` helper. Site rows (rows with `.children`) only pass by delegating to `anyChildMatches`, no longer via direct exact-match. Leaf rows use the direct check unchanged.
  - `renderTreeChildren` accepts an optional `passFilter` argument. Filters children through it when a non-'all' filter is active. Emits a "No projects here match this filter" placeholder when a site header made it through but all its children got filtered out (shouldn't happen given the site-visibility logic, but defensive).
  - `renderSitesTree` — call to `renderTreeChildren` now threads `pass` through as the sixth arg.
- `web/assets/versions.json`, `web/cloud.html` — version chip bump (skipped v4.9.12 in the release notes since it was an in-flight rev that shipped only Problem 1's fix; v4.9.13 has both).
