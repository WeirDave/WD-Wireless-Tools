WD Cloud Manager — new bulk "Share…" button in the toolbar lets you share multiple selected cloud projects with people and/or your Sharing Group in one action.

Suite `v1.9.53 → v1.9.54`. WD Cloud Manager `v4.9.1 → v4.9.2`.

## the maintainer's ask

> "can we make a batch sharing function where it would for example share all the selected files with the whole group?"

Yes — Ekahau's share endpoints already accept `projectIds` as an array (`POST /shareapi/v1/projects/users` and `PUT /shareapi/v1/projects/users/toggle-userGroup`), so N projects × M emails goes out in a single request. Just needed the WD UI to expose it.

## What it does

Tick multiple cloud projects in the ledger, click the new **Share…** button in the bulk toolbar (between Verify pairs and Delete selected). Modal appears with:

- **Add people**: a textarea accepting comma-, semicolon-, space-, or newline-separated emails. De-duplicates. Filters non-`@` tokens. Applies the selected role to every email.
- **Share with your Sharing Group** toggle (only rendered when we know your group id — auto-fetched on modal open via `get_my_group`). Enable + pick a role.
- Both actions can be applied in one submit — leave the textarea blank if you only want group sharing, or leave the toggle off if you only want to add people.

Backend uses Ekahau's array endpoints so:
- **Email adds**: one request adds ALL emails to ALL owned projects at once (`bulk_add_shares` — projectIds + emailAddresses both arrays).
- **Group toggle**: one request enables the group on ALL owned projects.

## Owner-gating

Ekahau's share endpoints reject non-owners with a 403. To avoid a confusing partial failure, the backend pre-checks ownership for every selected project (one `list_project_shares` call each — small tax, clearer results):

- Projects you own: proceed with the share.
- Projects you don't own: silently skipped, listed in the `skipped` field of the response.

The toolbar button reflects the same gating client-side: it only lights up when the selection contains at least one project where `cloud.owner === currentUser` (using the live OWNER field from v1.9.48, not the immutable createdBy). Tooltip on the enabled state names the count: *"Share 2 projects with people or your Sharing Group in one action"*.

## What the backend returns

Success response includes:
- `ownedCount` — how many projects the share was actually applied to.
- `skipped` — array of `{projectId, reason}` for anything the pre-check refused (usually "Not owner").
- `emailsAdded` / `role` — echoed back.
- `groupShared` / `groupRole` — echoed back if group toggle was enabled.

Frontend surfaces this as a summary toast: *"Shared 2 projects with 3 emails + group (0 skipped — not owner)"*.

## Verified in the preview

Steps run in the browser pane on the maintainer's real cloud:

1. Restarted Flask (Python changes), reloaded `/cloud`. Version chip: `v4.9.2`.
2. Selected 2 the maintainer-owned projects with checkboxes → toolbar button enabled, title reads *"Share 2 projects with people or your Sharing Group in one action"*, `window._bulkShareOwnedIds` stashed both project IDs.
3. Clicked Share… → modal opens titled *"Share 2 projects"*, subtitle explains the flow.
4. Verified all three form elements render correctly:
   - Emails textarea with helpful placeholder + `View only`/`Edit rights`/`Full access` role select.
   - Group toggle row appears (group auto-fetched, rendered with the same iOS-style switch as the individual modal) + `View only`/`Edit rights`/`Full access` group role select.
   - "Apply to selected" button in the footer.
5. Cancelled without submitting to avoid mutating live shares.

**Not tested**: actual mutation. The payload shape is lifted from the maintainer's own captured session where the same endpoint returned success, and the same code path already powers the single-project add/toggle flows in production. Confidence is high; end-to-end proof needs a real click.
