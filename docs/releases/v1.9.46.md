WD Cloud Manager — Manage Sharing modal grows a "Danger zone" section with two-stage ownership transfer for project owners. Wires Ekahau's `/shareapi/v1/projects/users/transfer-ownership` endpoint (captured against a throwaway sample-project.esx).

Suite `v1.9.45 → v1.9.46`. WD Cloud Manager `v4.8.3 → v4.8.4`.

## the maintainer's ask

> "There is also a transfer ownership option. I personally won't be doing this but someone out there might"

Followed by a live capture — the maintainer uploaded sample-project.esx, ran a real transfer to teammate-a@example.com with the sniffer installed, and shared the JSON. That gave us the definitive endpoint + payload shape instead of guessing.

## Endpoint

- **`POST /shareapi/v1/projects/users/transfer-ownership`**
  ```json
  {
    "projectOwnershipTransferDetails": [
      {"projectIds": ["<uuid>"], "currentOwnerEmailAddress": "you@example.com"}
    ],
    "newOwnerEmailAddress": "recipient@example.com"
  }
  ```
- Response: `200 OK` with `{"<projectId>": "SUCCESS"}` on success.
- Payload technically supports batch (multiple projects per current-owner block, multiple blocks per call) — we only expose single-project transfers in the UI because batch would need a very different confirmation flow.

## What actually happens on transfer

Observed in the capture's follow-up `list_shares`:

- **Old owner → READ_USER** (kept as viewer, not removed — small mercy)
- **New recipient → OWNER** (regardless of whether they were previously in the shares or via group)
- **Group-linked members lose their `groupId`** — before transfer, a teammate was WRITE_USER with `groupId: <the maintainer's group>`; after, he's OWNER (no groupId). a teammate (also via the maintainer's group) stayed WRITE_USER but his `groupId` link disappeared too. Makes sense: the maintainer's group is the maintainer's; ownership moving to a teammate orphans those group associations.

The confirmation copy in the UI now says this plainly: "Any group-shared members will remain as individual shares (their group link breaks)."

## UI — Danger zone with two-stage confirm

New `#shareDangerSlot` between the "Share with someone" block and the Close button. Rendered ONLY when the signed-in user is the OWNER of this project (checked by comparing `#userEmail` textContent against the OWNER role in `list_shares` response).

**Stage 1 (idle)** — one-line hint ("Transfer ownership — hand this project to another user. You'll keep view-only access"), an email input, and an outlined-red "Transfer…" button. Enter or click advances to stage 2.

**Stage 2 (confirm)** — replaces the row with a red-highlighted warning box explaining consequences (demoted to View only, group associations break, action is irreversible without the new owner's help), then requires typing the recipient email a second time. Solid-red "Transfer" commits; blue "Cancel" backs out to idle. Mismatched retype rejects with a toast: `Type "recipient@example.com" exactly to confirm`.

Two-stage exists because Ekahau's own transfer flow is one confirmation button-click away from a permanent role loss. Retype-to-confirm matches the severity better than a plain OK button.

## Server-side safeguards

- `CloudManager.transfer_ownership` derives the current owner from `list_project_shares` rather than trusting a client-supplied email — prevents "wrong owner" 403s from stale frontend state.
- Fails fast with a friendlier message than the raw 403 when the signed-in user isn't the current owner (`"Only the owner (X) can transfer this project"`).
- Rejects self-transfers (`"X is already the owner"`) client-side too.
- Response parsing checks the per-project status field; anything other than `SUCCESS` returns as an error rather than a silent success.

## CSS layout fix

First cut of the confirm-row buttons overlapped visually — I'd tried to reuse `.share-add-row`'s 3-column grid with `auto auto` appended for two buttons, but hiding the middle "role select" span with `display: none` removes it from the grid entirely, so the remaining children shift into wrong columns (Transfer landed on the 0-width slot, sitting UNDER Cancel). Fixed by dropping the shared grid inheritance: `.share-danger-confirm-row` and `.share-danger-form` now own their own grid template (`minmax(0, 1fr) auto auto` and `minmax(0, 1fr) auto` respectively).

1. Restarted Flask, reloaded `/cloud`, opened a share modal on a the maintainer-owned project.
2. Danger zone visible with "Danger zone" label + "Transfer…" button (as expected, since signed-in user matches OWNER).
3. Typed `teammate-a@example.com` → clicked Transfer… → confirm stage rendered with red warning box, retype input, and Transfer + Cancel buttons.
4. Measured: Transfer/Cancel have a clean 8px gap between them; Cancel's right edge sits 38px inside the modal edge (no clipping). Screenshot matches spec.
5. Clicked Cancel → back to idle stage cleanly (start form + "Transfer…" button restored).
6. Re-entered confirm → typed WRONG email (`wrong@example.com`) → clicked Transfer → rejected with toast `Type "teammate-a@example.com" exactly to confirm`, still in confirm stage. Guard works.
