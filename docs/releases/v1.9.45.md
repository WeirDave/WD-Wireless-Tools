> "yes they do I showed you the webpage of the group"

Correction to my prior claim that Ekahau didn't have a captured endpoint for the sharing group. the maintainer grabbed a capture of `/manage` after I fixed the sniffer script's unescaped-newline bug and confirmed **both** the list endpoint AND the mutation endpoint live under a separate namespace: `/userapi/v1/*` (not `/shareapi/v1/*` like everything else so far).

## Endpoints wired

- **`GET /userapi/v1/userGroups?groupName=<encoded>`** — returns an array of groups, each with `groupId`, `groupName`, `createdBy`, and full `members` list. We take the first match. Default query is "My Sharing Group" (Ekahau's per-user default).
- **`PUT /userapi/v1/userGroups`** — the mutation endpoint. Body shape captured is asymmetric:
  - **Add**: `{addedMemberList: [email], deletedMemberList: [], members: [], groupId, groupName, createdBy: ""}`
  - **Remove**: `{addedMemberList: [], deletedMemberList: [email], members: [<full current member list>], groupId, groupName, createdBy: ""}`
  - Response is `204 No Content` in both cases.
- Wrapped as `EkahauAPI.get_user_group()` (auto-decodes response array) and `EkahauAPI.update_user_group(group_id, name, added=[], deleted=[], current_members=[])` (normalizes add vs remove payload asymmetry so callers just pass the delta).

## Group discovery — no more opportunistic learning

Prior version cached `{id, name}` to `localStorage` only when a `list_shares` response happened to include a user with a `groupId`. First-touch discovery problem: on projects where the group wasn't already active, the toggle didn't render.

Now: `openManageShares` fires `get_my_group` in parallel with `list_shares` on every modal open. Group renders reliably regardless of project state, and the members list is always fresh (they can change from outside WD via Ekahau's own web UI). `localStorage` cache retained as a warm-render optimization — toggle appears instantly while the fetch is in flight — plus opportunistic learning kept as a fallback if the endpoint ever fails.

## Members management UI

New "Manage members (N) ▸" chip under the group toggle row. Rendered only when the live fetch succeeded (member count is real, not cached). Click → expands inline panel showing:

- **One row per member** — full name + email + × remove button
- **Add-email input + "Add to group" button** — email validation, duplicate detection (server-side too), Enter-to-submit
- **Hint text** — "Anyone in this group can be added to any project in one click via the toggle above. Changes here affect the group globally, across all your projects." — so users understand scope isn't project-scoped.

Remove requires confirm with explicit copy: "Remove {email} from your Sharing Group? They'll lose access to every project the group is shared with."

Backend enforces email validation (`@` required) and skips no-op adds when the email is already a member (returns `{ok: true, already: true}` so the UI can toast "already in the group").
