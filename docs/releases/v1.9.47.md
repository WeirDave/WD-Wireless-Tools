WD Cloud Manager — Transfer ownership now matches Ekahau's own rule (target must already be shared), picks from a dropdown instead of free-form email, and drops the retype-to-confirm step in favor of a big red button naming the recipient. Also fixes a backend bug that made the transfer API throw before it could reach Ekahau.

Suite `v1.9.46 → v1.9.47`. WD Cloud Manager `v4.8.4 → v4.8.5`.

## the maintainer's ask

> "The transfer option is only active after your file is shared then you can transfer to that selected email only"

the maintainer's screenshot of Ekahau's own web UI proved this — "Transfer ownership" appears inside each shared user's per-row role dropdown (alongside "Full access", "Edit rights", "View only", "Remove access"). If someone isn't shared, they never appear in that list, so there's no way to transfer to them via Ekahau's UI. My previous release's free-form email input would have let users type any address and hit an API rejection — bad UX.

## Danger Zone — now dropdown-driven

Rework of the same slot at the bottom of the Manage Sharing modal (still owner-only). Three states:

- **Idle (with shares present)**: dropdown labeled "Choose new owner…" listing every non-OWNER user already on the project (individual + group). Selection required before "Transfer…" activates. Format: `Firstname Lastname (email@company.com)`.
- **Idle (no other shares)**: dropdown is replaced by a helpful hint: *"Ekahau only lets you transfer to someone who already has access to this project. Share it with them first (using the 'Share with someone' form above), then come back here."*
- **Confirm**: warning box (same copy as before — old owner drops to View only, group associations break, action is irreversible) + one big solid-red button labeled `Transfer to <recipient@email>` + a Cancel button.

Retype-to-confirm removed — the dropdown already constrains the choice to a small named set, and the big button names the specific recipient. Retyping the same email into an input right after picking it from a dropdown was pointless friction.

## Backend bug fix

Field-tested against sample-project.esx (which now lives under teammate-a@example.com per an earlier capture), calling `POST /api/cloud/transfer_ownership` returned:

```
{"error": "'str' object has no attribute 'get'"}
```

Root cause: `EkahauAPI.list_project_shares(project_id)` returns `{project_id: [user_dict, ...]}` (a dict keyed by project id), but `CloudManager.transfer_ownership` was treating the return as a flat list — iterating over the dict yielded string keys, and `.get("role")` blew up. The existing `list_shares` wrapper had the correct extraction pattern (`(result or {}).get(project_id, [])`); I just hadn't copied it into the transfer path.

Fix in `tools/cloud_manager.py`:
```python
raw = self.api.list_project_shares(project_id) or {}
shares = raw.get(project_id, []) if isinstance(raw, dict) else []
```

Now the API call works: hitting `transfer_ownership` for sample-project.esx (which the maintainer doesn't own anymore) correctly returns `"Only the owner (teammate-a@example.com) can transfer this project"` instead of throwing.

## Also noticed — stale ledger owner display

the maintainer pointed out that WD's ledger still shows `(owner@example.com)` as the owner of sample-project.esx, even though the live Ekahau share list has teammate-a@example.com as OWNER. That's a real WD bug: the ledger reads owner from `history.createdBy` (immutable, always the original creator), not from the live shares list. Fixing it properly needs a batch call to `list_project_shares` for every scanned project so the display reflects current ownership, not creation ownership. Spun off as a follow-up task rather than bundling into this release since it's a bigger scan-path change.
