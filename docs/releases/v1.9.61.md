WD Cloud Manager — site-level match badges now read "Same site" (green) instead of "Name matches" (yellow), reflecting that name-match IS the strongest possible match for a site pair.

Suite `v1.9.60 → v1.9.61`. WD Cloud Manager `v4.9.10 → v4.9.11`.

## the maintainer's ask

> "Folders and sites shouldn't they be categorized differently because if there are equals they're always going to be name matches they're never going to be same file. If their name actually matches really it should say same site like same file. The name matches is exclusive to the projects which is true because the only validation you can do on a site compared to a folder is a name match"

Exactly right. Projects have three tiers of pairing evidence:

1. **Same file** — hidden UUID inside both `.esx` archives matches (proven byte-identical projects)
2. **Name matches** — filenames identical, no UUID link (very likely same project, not proven)
3. **Similar name** — fuzzy match, worth double-checking

Sites don't have (1) — there's no UUID inside a folder to compare. So the strongest match a site pair can ever achieve is (2), name-match. Rendering that with the same yellow "Name matches" badge implies there's a stronger match somewhere that just wasn't reached, when in fact the strongest possible IS a name match.

## Fix

- **Badge label for site pairs**: `✓ Name matches` (yellow, `mb-exact`) → `✓ Same site` (green, `mb-id`). Same green visual tier as project-level "Same file" — because for sites, this IS the equivalent strongest-match state.
- **Badge tooltip**: `"Both sites share the same name. Sites don't have a stronger identity to compare (folders have no internal ID), so this is as matched as a site pair gets."`
- **matchBadgeHtml** now accepts an optional `kind` argument. `gutCell` passes its resolved `kind` value through so the badge can distinguish site pairs from project pairs. When `kind === 'sites'` and `matchType === 'exact'`, the new `MATCH_BADGE_SPEC_SITE_EXACT` is used instead of the generic exact spec.
- **Project-level "Name matches" behavior is unchanged** — projects can still reach the higher "Same file" state, so their yellow "Name matches" correctly signals "not yet at the strongest tier".

## Also — explaining the "Name matches count dropped" observation

the maintainer noticed the Name Matches count went from ~30 down to 4. That's real, not a bug. When you ran the Verify workflow earlier (per-row ⇩ / bulk Verify pairs), it downloaded cloud copies and overwrote local `.esx` files — making them byte-identical, which promoted them from `matchType='exact'` to `matchType='id'`. Every one of those transitions took a row out of the Name Matches count and into the (invisible-but-present) Same file column. The 4 remaining are the ones that haven't been verified yet.

The visible-count and the badges now agree with each other after this release:

- Site pairs that share a name → "Same site" badge (green), NOT counted in Name Matches.
- Project pairs sharing a name only → "Name matches" badge (yellow), counted in Name Matches.
- Any pair with `matchType='id'` → "Same file" / "Same site" (green), NOT counted.
